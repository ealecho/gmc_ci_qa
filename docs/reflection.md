# Reflection on Git, CI, and Quality Assurance

Learning Git, continuous integration, and quality assurance together was challenging because each tool exposes a different type of mistake. Git required me to understand the difference between local branches, remote-tracking branches, and repository histories. The most difficult part was working safely with a second repository that already had an unrelated initial commit. I learned to inspect remotes and commit graphs before pushing, preserve existing work, and use feature branches and explicit merges instead of force-pushing.

Configuring CI also required careful sequencing. A build can succeed while linting or tests fail, so the pipeline needed separate, visible gates. Using a lockfile installation, linting with zero tolerated warnings, regenerated cloud types, TypeScript checks, unit tests, a production build, and a deployment dry run made failures easier to locate. The pipeline streamlined development by turning the complete verification process into one repeatable workflow. A contributor no longer needs to remember every command, and reviewers can see objective results for the exact commit being proposed.

QA practices improved the code in concrete ways. ESLint identified an unnecessary empty interface and a React effect pattern that lacked request cancellation. Unit tests verified strict dates, input limits, allowed locations, and Bearer-token parsing. Manual review also checked secret handling, public-data exposure, and prepared database queries. Version control made these changes traceable and reversible, while branching allowed quality work to be reviewed before integration. Together, these practices reduced reliance on individual memory, made collaboration safer, and provided evidence that the application was not only functional but consistently reproducible and reviewable.
